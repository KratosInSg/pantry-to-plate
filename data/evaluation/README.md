# `data/evaluation/` — the frozen benchmark

Synthetic "simulated kitchens" used to compare planning methods. **Do not edit by hand.** It is generated by
`python src/evaluation/build_benchmark.py` and verified by hash on every load.

| File | What |
| --- | --- |
| `scenarios_v1.jsonl` | 240 scenarios (8 families × 30 seeds), one JSON object per line (`domain.models.Scenario`) |
| `split_v1.json` | Stratified split by family: 120 `validation`, 120 `test` scenario ids |
| `FROZEN.json` | Version, creation date, SHA-256 of the two files above and of the dataset `MANIFEST.json` |
| `runs/` | Per-run result CSVs written by `runner.py --save` (git-ignored; derived) |

## Rules

1. **Frozen before tuning.** The split exists before any optimiser weight was tuned.
2. **Tune on `validation` only.** The `test` split is run once, at the end, with the weights fixed.
3. **Changing the generator = a new version.** Bump `BENCHMARK_VERSION` in `src/evaluation/scenarios.py`, generate into
   fresh files, and re-run every comparison; numbers from a previous version no longer apply.
4. `load_split` raises if either file no longer matches `FROZEN.json`.

## What a scenario contains

A user profile (diet, allergens, exclusions, likes/dislikes, time and kcal targets), a pantry of ingredient ids with
grams, the **planner-visible** deadline for each item (known date or estimate with a confidence) and — for the
simulator only — the **hidden true** last usable day. Planners never read the hidden truth.

See `md docs/modules/evaluation/scenarios.md` for the eight families and the generator's decisions, and
`md docs/evaluation.md` for the metrics.
